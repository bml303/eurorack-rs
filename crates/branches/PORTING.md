# Branches -- port status

**Dual Bernoulli gate**  |  MCU family: `avr`

## Status: PORTED (fixed-point, follows the shipping firmware)

Branches is a single 305-line file with no separate DSP/UI split, no
`resources.cc`, and almost no algorithmic content -- it's essentially a
hardware main loop (GPIO gate I/O, ADC polling, an EEPROM-backed long-press
UI, LED refresh) wrapped around a genuinely tiny probabilistic core. That
core is what's ported here.

### Modules

| Rust file | C source | notes |
|-----------|----------|-------|
| `src/resources.rs` | `branches.cc`'s `linear_table` | transpiled (see below -- no separate `resources.cc`/`.h` pair exists for this module) |
| `src/rng.rs` | `branches.cc`'s `rng_state` | a 32-bit Galois LFSR, feedback polynomial `0xd0000001`, hand-inlined in the C rather than using `avrlib::Random` |
| `src/lib.rs` | `branches.cc`'s `Read`/rising-edge decision block in `main` | `Channel` (one channel's gate decision) + `Branches` (both channels + the shared RNG) + `probability_to_threshold` |

Out of scope: all GPIO/ADC/EEPROM access (`Init`, `Read`, `ReadSwitch`,
`GateOn`/`GateOff`, `LedOff`, the ADC ping-pong polling in `main`), the
switch long-press state machine that flips `toggle_mode`/`latch_mode` and
persists them to EEPROM (`DisplayConfigurationAndSave`, `kLongPressTime`,
`press_time`/`inhibit_switch`) -- a host sets `Channel::toggle_mode`/
`latch_mode` directly instead, the same way every other crate in this
workspace drops `LoadSettings`/`SaveSettings` -- and LED state (`led_state`,
`led_gate_delay`).

### Resources: transpiling a table with no `resources.cc`/`.h` pair

Every other AVR crate in this workspace transpiles a `resources.cc`/`.h`
pair generated by `resources/resources.py`. Branches has neither -- its one
lookup table (`linear_table`, 256 entries, `uint16_t`, `PROGMEM`) is
declared directly in `branches.cc`. `tools/transpile_resources.py` only
actually *reads* its first argument (the `.cc` path); the `.h` argument is
accepted but unused. So this port ran it directly against a `sed`-
preprocessed copy of `branches.cc` itself (same `prog_uint16_t`->`uint16_t`
/ drop `PROGMEM` substitution as `mi-edges`/`mi-grids`), passing the same
path twice, and kept just the one resulting array.

### Deviations from the C++

* `Channel`/`Branches` are ordinary instances, not `static` globals --
  matching every other crate in this workspace (`branches.cc`'s module-level
  `bool toggle_mode[2]` etc. are C's usual AVR-firmware singleton idiom).
* The RNG snapshot/advance timing is preserved exactly: the firmware's main
  loop captures `random_words = rng_state` once per iteration, consumes its
  low 16 bits for channel 0 and next 16 bits for channel 1, and only
  advances `rng_state` afterward for the next iteration.
  [`Rng::next_words`] reproduces this as one call: it returns the
  pre-advance snapshot and updates the state as a side effect, so
  `Branches::step` can split that single snapshot across both channels the
  same way.
* `Channel::step` takes an already-computed `threshold: u16` rather than an
  ADC channel index -- the ADC-to-probability pipeline
  (`p[i] = linear_table[adc.ReadOut8()]`, refreshed roughly once per main
  loop iteration in a ping-pong fashion across the two channels) is a
  hardware polling detail; a host calls [`probability_to_threshold`] on
  whatever ADC reading it has, whenever it has one, and passes the result
  in.

### Verification

No C bit-compare harness (no host-buildable C test for this module).
`tests/smoke.rs`: the two fully-deterministic edges of the gate decision
(`threshold == 0` always passes a rising edge, `threshold == 65535` always
blocks regardless of the random draw -- both hold for every input in the
loop, not just spot checks), toggle mode's flip-flop behaviour under a
deterministic draw, latch mode holding the gate through a falling edge vs.
non-latch dropping it immediately, a 20,000-step two-channel sweep across
every toggle/latch combination, `probability_to_threshold`'s monotonicity
and range, and 200,000 RNG draws that must never settle at the LFSR's
all-zero absorbing state.

### A real bug this port's fidelity check caught

None found in this module -- its logic is small enough (`outcome = random
>= threshold && threshold != 65535`, a single XOR for toggle mode, a single
latch-mode branch) that there was no room for an out-of-bounds read or a
missed edge case to hide in.

## Not in scope for the library crate

STM32/AVR peripheral drivers, the audio bootloader, and the
`hardware_design/` files stay in the C repo -- the Rust crate is a `no_std`
DSP library that a host or an embedded HAL feeds.
